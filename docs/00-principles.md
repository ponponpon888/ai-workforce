# 00. 原則

English: [00-principles.en.md](00-principles.en.md)

## 前提の共有

私はエンジニアではありません。13 年、ホテルと旅館の支配人をしていました。
コードは読めますが、レビューで間違いに気づける水準ではない。

この一点が、ここに書いてあるすべての設計理由です。

一般的な「AI 開発術」は、暗黙のうちに **人間が最終レビューできる** ことを前提にしています。
AI が書いた SQL を見て「あ、WHERE がない」と気づける人向けの話です。
私はそれができない。だから、気づけなくても壊れない構造を先に作るしかなかった。

---

## 8:2

| 割合 | 誰が | 何を |
|---|---|---|
| 8 | AI | コードを書く / 調べる / 直す / テストを通す |
| 2 | 人間 | 何を作るか決める / 本番に触る前に止める / 責任を取る |

この比率は「AI にどれだけ任せるか」の話ではありません。
**人間にしか担えない 2 割が何なのかを、はっきりさせるための線引き**です。

その 2 割は、具体的には次の 4 つでした。

### 1. 何を作るかを決める

これは AI に渡せません。渡すと、それらしいが誰も使わないものが出てきます。
私の場合、判断材料はコードではなく現場です。13 年ホテルにいたので、
「予約が入った瞬間に現場で何が起きるか」は分かる。そこが唯一の強みです。

### 2. 本番に触る前に止める

AI は悪意なく本番を壊します。悪意がないので、止め方も「注意する」では効きません。
**実行前に、機械が落とす**。これが [02 機械的な歯止め](02-guardrails.md) の全部です。

### 3. 取り消せるかどうかで線を引く

これが運用上いちばん効きました。

- 取り消せる（ブランチ、PR、デプロイ、調査）→ **確認を取らずに進めてよい**
- 取り消せない（DROP、削除、課金、送信済みメール）→ **必ず止まる**

以前は「実装前に毎回確認」にしていました。安全ですが、確認が多すぎて読まなくなります。
読まずに OK を押している確認は、確認していないのと同じで、しかも「確認した」という感覚が付く分だけ悪い。
線を「取り消せるか」に引き直したら、確認の回数が 1/10 になり、
残った確認は全部ちゃんと読むようになりました。

### 4. 責任を取る

AI は責任を取りません。ユーザーに謝るのは私です。
だから、AI が「たぶん大丈夫」と言った箇所は、私が「大丈夫だと決めた」箇所になります。
その自覚を持てる粒度まで、AI に説明させます。

## 三つのルール

### 埋めた箇所を必ず言わせる

一番危ないのは、仕様の穴を AI が黙って埋めることです。
コードは動く。テストも通る。でも、決めたつもりのない仕様がそこにある。

だから共通 `CLAUDE.md` で、毎回これを出力させています。

```
## 触った範囲
- 依頼された範囲: ...
- 依頼外に触った箇所: ...（なければ「なし」）

## 埋めた箇所
- 仕様が決まっていなかったので推測で決めた点: ...
- 根拠: ...
```

訂正できる状態を保つ。それだけのためのセクションです。

### 事故が起きてからしか課題化しない領域を、先に入れさせる

権限、冪等性、送達保証、監査。
この 4 つは、依頼書に書かれることがまずありません。書かれるのは事故の後です。

私は事故の経験値が足りないので、書かれていなくても最初から入れさせています。
「言われていないので入れませんでした」は、非エンジニアが一人でやる開発では致命傷になります。

### 速度のために安全を削らない

開発速度はもう十分に出ています。ここから先、速度のために安全を削っても、
得られるのは「速く壊れる」だけです。

## この構成にたどり着くまでに踏んだもの

正直に書いておきます。ここに書いてあるルールは、全部あとから足したものです。

- 別プロジェクトのディレクトリで作業を実行された（→ [04](04-multi-project.md) の絶対パス指定）
- 承認を毎回求める設定にしていたら、承認が形骸化した（→ 取り消せるかで線を引き直し）
- 構造化データが SSR の HTML に出ていないことに数か月気づかなかった（→ 各プロジェクトの「既知の落とし穴」）
- PowerShell 5.1 が BOM なし UTF-8 を化けさせて、原因究明に半日使った（→ [02](02-guardrails.md) の encoding 節）

先に設計したのではなく、踏んで、そのたびに機械で塞いだ結果がこれです。

## 一番大きく踏んだもの

2026 年 1 月に、AI エージェントの SaaS を作ろうとして 14 日で止めました。
そのリポジトリは残してあります。何がどうダメだったかを書き足して、いずれ公開します。

読み直して分かったことが 4 つあって、このリポジトリはほぼその 4 つへの回答です。

### 1. 見た目から作った

UI テーマを 6 回作り直していました。Marketplace → War Room → Visual Editor →
Neural Glow → Hex Grid → GlobalSidebar。最初の 6 日で機能を組んで、残りの 8 日は全部それです。

その間、**データの流れを一度も端から端まで通していませんでした。**
結果、ダッシュボードは構造上ずっと空でした。書き込み側は `ai_type: 'code_generator'`、
読み込み側のフィルタは `['email','daily_report','apology','summary','idea']`。一件も一致しない。

止めるまでの 2 週間も、放置していた 7 ヶ月も、空のダッシュボードを
「まだデータが溜まっていないだけ」だと思っていました。読み直すまで気づいていません。

### 2. ビルドが通ることを確認していなかった

コミットしてあったビルドログは、全部失敗でした。成功した記録が 1 本もない。
「たぶん通る」で次に進んでいたということです。

→ いまは各プロジェクトの `CLAUDE.md` に `npm run build` を「push 前に必ず通す」と書いています。
　このリポジトリ自体も、CI でスクリプトのパース・非 ASCII 検査・guard-sql 29 ケース・
　pull-all 23 ケース・インストーラの実行を、Ubuntu / macOS / Windows で回しています。

### 3. マイグレーションを残していなかった

`.sql` ファイルが 0 件でした。DB スキーマは Supabase 上にしか存在しない。
しかも `ai_activities` と `usage_logs` という別スキーマが同じアプリの中で併存していて、
いまとなってはどちらが正なのかも分かりません。

→ [05 本番 DB の取り決め](05-production-db.md)。スキーマの変更は必ずマイグレーションに残す。
　DDL を承認制にしているのも、ここが理由の一つです。

### 4. 誰が使うかを書いていなかった

README が `create-next-app` のテンプレートのままでした。
当時の自分が誰に売るつもりだったのか、リポジトリから読み取れません。

→ これは仕組みでは塞げないので、プロジェクトを始めるとき最初に README を書くようにしました。
　[案件別 `CLAUDE.md` のテンプレート](../kit/project-templates/nextjs-supabase-CLAUDE.md)の
　冒頭が「何のサービスか／機能一覧ではなく目的を書く」から始まるのは、そのためです。
