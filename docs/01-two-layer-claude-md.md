# 01. 2 層の CLAUDE.md

## 結論

| ファイル | 置き場所 | 書くもの | 変更頻度 |
|---|---|---|---|
| 共通 | `~/.claude/CLAUDE.md` | **安全ルールだけ** | ほぼ変えない |
| 案件別 | `<project>/CLAUDE.md` | **技術構成と固有の事情だけ** | よく変える |

混ぜないこと。これが全部です。

---

## なぜ分けるのか

最初は案件ごとの `CLAUDE.md` に安全ルールも書いていました。すぐ壊れました。

理由は単純で、案件別ファイルは**よく編集される**からです。
新しいライブラリを入れた、ディレクトリを変えた、と触っているうちに、
安全ルールの行が少しずつ古くなり、案件によって内容がずれていきます。

そして一番まずいのは、**新しく作ったプロジェクトに安全ルールが載らない**こと。
新規プロジェクトは、いちばん事故が起きやすい場所です。そこだけ無防備になる。

安全ルールは変わらない。技術構成は変わる。
更新頻度が違うものを同じファイルに置いてはいけない、というだけの話でした。

---

## 共通レイヤーに書くこと

`~/.claude/CLAUDE.md` — 全案件に無条件で効きます。

書くのは 4 種類だけです。

1. **止まるべき場所**（DROP、WHERE なしの UPDATE、`.env` の読み取り、force push…）
2. **進めてよい場所**（取り消せる操作は確認不要）
3. **報告の義務**（触った範囲・埋めた箇所を毎回書かせる）
4. **環境の制約**（PowerShell、BOM なし UTF-8、`.ps1` に日本語を書かない）

実物: [kit/claude/CLAUDE.md](../kit/claude/CLAUDE.md)

**書かないこと:** 技術スタック、npm スクリプト、ディレクトリ構成、URL。
これらを共通に書くと、案件が増えるたびに共通ファイルが肥大して、読まれなくなります。

## 案件レイヤーに書くこと

`<project>/CLAUDE.md` — そのプロジェクトを開いたときだけ効きます。

テンプレート: [kit/project-templates/nextjs-supabase-CLAUDE.md](../kit/project-templates/nextjs-supabase-CLAUDE.md)

このレイヤーで一番価値があるのは、機能一覧でも構成図でもなく、
**「既知の落とし穴」** のセクションです。

実例:

```markdown
## 既知の落とし穴

- JSON-LD はサーバーコンポーネントの素の `<script>` で出す。
  `next/script` の `<Script>` はクライアント側挿入で SSR の HTML に残らず、
  JS を実行しない AI クローラには届かない。
  （FAQ 構造化データが長期間 HTML に出ていなかった。発見まで数か月）

- `app/layout.tsx` の `metadataBase` が apex だが、実配信は www 付き。
  canonical は www 付きの絶対 URL で書いて回避している。
```

一度踏んだ落とし穴を、AI が二度目に踏まないための場所です。

正直に言うと、私自身このセクションを埋め切れていません。稼働中の 3 本のうち 2 本は
`CLAUDE.md` に落とし穴を書いていない（[事例](case-studies/)に書いた通りです）。
効果を数字で示せる立場にはありません。**やるべきだと思っているが、まだやれていない**が実態です。

---

## 運用のコツ

**共通ファイルを長くしない。** 200 行を超えたら、それは案件別に書くべき内容が混ざっています。

**案件ファイルに安全ルールを再掲しない。** 再掲すると、片方だけ更新されて食い違います。
食い違ったルールは、ルールがないより悪い。

**落とし穴は踏んだその日に書く。** 後で書こうとすると、原因の記憶が薄れて
「なんか動かなかった」しか残りません。それでは再発を防げません。
