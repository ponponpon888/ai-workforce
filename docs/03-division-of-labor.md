# 03. 役割分担

同じモデルでも、置き場所で得意が変わります。
「どこで何をやらせるか」を固定しておかないと、遅い場所に重い仕事が流れます。

---

## 結論

| どこ | やること | やらせないこと | 理由 |
|---|---|---|---|
| **チャット**（Cowork / claude.ai） | 設計・判断・調査・仕様を固める・文章 | ローカルの git 操作、ネイティブビルド | git 認証が通らない。Windows ネイティブの `node_modules` を動かせない |
| **手元の Claude Code** | ファイル操作・git・ビルド・テスト・実装 | 仕様を勝手に決めること | ここが一番速い。ただし文脈は狭い |
| **GitHub MCP** | PR 作成・レビュー・マージ | — | チャットから直接 PR まで行ける案件はこれが最短 |

---

## 分担が決まるまで

最初は、チャットで編集済みファイルを作らせてダウンロードし、
PowerShell の `Copy-Item` で所定の位置に置いていました。

これはこれで理由があって、**その場で文字列置換するスクリプト**を走らせるより安全だからです。
置換スクリプトは、対象が想定と違ったときに静かに壊れます。ファイルごと差し替える方が結果が読める。

ただ、往復が多すぎました。

いまは:

- **設計・判断はチャット**（文脈が長く持てる。複数プロジェクトを横断できる）
- **ファイル操作は手元の Claude Code**（ダウンロード → `Copy-Item` を挟まない）
- **GitHub MCP が繋がっている案件は、チャットから直接 PR・マージまで**

チャット側から手元のリポジトリを触ろうとすると、git 認証で止まります。
これは設定でどうにかする話ではなく、**そもそも向いていない**と割り切った方が早い。

---

## ダウンロードするファイルの命名

チャットからファイルを受け取るなら、名前で必ず事故ります。

`route.ts` を 3 回ダウンロードすると、Downloads フォルダに
`route.ts` / `route (1).ts` / `route (2).ts` が並びます。どれが最新か分からない。

なので **用途 + 対象 + バージョン + 日付** で名前を付けます。

```
route_onboarding_parking_v4_20260824.ts
schema_person_jsonld_v2_20260901.ts
```

長いですが、Downloads フォルダで迷子にならないことの方が大事です。

---

## 手元の Claude Code に投げるときの必須事項

**プロンプトの冒頭に絶対パスを書く。** 毎回です。

```
C:\Dev\musubu で作業してください。
（以下、依頼内容）
```

理由: 別プロジェクトのディレクトリで作業が実行された事故があります。
`musubu` の作業を `hanami-nail-prototype` で実行された。
どちらも Next.js + Supabase なので、途中まで普通に動いてしまう。

共通 `CLAUDE.md` にも、作業前に `pwd` で一致を確認するルールを入れていますが、
**プロンプト側にも書く**。二重にします。安いので。

## 承認モードの変遷

正直に経緯を書いておきます。

| 時期 | 設定 | やめた理由 |
|---|---|---|
| 初期 | 実装前に毎回確認 | 確認が多すぎて形骸化した |
| 次 | 自動承認 | セッションごとに 1 回ダイアログが出るのが面倒 |
| いま | 承認をスキップ（取り消せない操作だけ手で止める） | — |

**これはチャット側の話です。** 手元の Claude Code は `settings.json` で `defaultMode: "ask"` 固定、
bypass モードにも入れないようにしてあります（[02](02-guardrails.md)）。

チャット側の設定には、**機械的な歯止めがほとんどありません**。
`guard-sql` と `deny` リストは手元の Claude Code にしか効かないので、
チャットから叩く Supabase / GitHub / Vercel は素通りです。

Supabase については塞ぎ方が分かりました。接続 URL に `read_only=true` と `project_ref` を付けて、
本番プロジェクトは繋がない → [06 チャット側の穴を塞ぐ](06-supabase-mcp.md)。

GitHub と Vercel も調べました → [07 GitHub と Vercel の穴](07-github-vercel.md)。

GitHub は思っていたより細かく絞れます（MCP の `--read-only` / `--exclude-tools` / `--lockdown-mode`、
fine-grained PAT、ruleset）。ひとつ大きな発見があって、
**force-push とブランチ削除はトークンのスコープでは止められません**。
`Contents: Read and write` が普通の push も force-push も削除も同じ 1 権限で許すためで、
止めるのはリポジトリ側の ruleset です。

**Vercel はまだ絞りきれていません。** 一番効くのは Vercel の設定ではなく、
本番デプロイを Git 連携に一本化して `main` を ruleset で守ること。
そうすると GitHub 側の歯止めがそのまま Vercel の歯止めになります。

承認を切るなら、切った分だけどこかで埋め合わせが要ります。
長いあいだ、埋め合わせをしないまま切っていました。
