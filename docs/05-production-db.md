# 05. 本番 DB の取り決め

English: [05-production-db.en.md](05-production-db.en.md)

AI に本番の Supabase を触らせるかどうかは、この構成でいちばん怖い部分です。
触らせないのが一番安全ですが、それだと運用が回りません。

なので、線を引きました。

---

## 4 つの取り決め

### 1. DDL は、内容を提示して承認を取ってから実行する

`CREATE` / `ALTER` / `GRANT` / `REVOKE` は、SQL の全文を見せてもらってから承認します。

これは口約束ではなく、[02 のフック](02-guardrails.md)で機械的に強制しています。
承認トークンがないと通りません。承認したその文が、15 分だけ、1 回だけ通る。

### 2. `UPDATE` / `DELETE` は `WHERE` 必須

例外なし。フックが落とします。

「全件更新したい」ケースは実在しますが、そのときは `WHERE true` と明示的に書きます。
書けば通ります。**書かせることに意味がある**ので、そうしています。

### 3. `DROP` / `TRUNCATE` は実行しない

エージェントからは通しません。必要なら人間が Supabase の管理画面で手でやります。

年に数回あるかないかの操作のために、自動化の口を開けておく理由がない。

### 4. テストデータには、消せる印を必ず付ける

本番でテストデータを入れることは、実際にあります（本番でしか再現しない不具合など）。

そのときは `admin_memo` に **用途と「削除可」** を書きます。

```sql
insert into salons (name, admin_memo)
values ('テスト用サロン', '2026-09-06 掲載フロー検証用 / 削除可');
```

そして、**確認後に必ず消します**。
「あとで消す」は消えません。印を付けるのは、忘れた自分が後から見つけられるようにするためです。

## 開発と本番を物理的に分ける

Supabase のプロジェクト自体を分けています。
`.env.local` と Vercel の環境変数で切り替え、**本番の接続情報はローカルに置きません**。

そのうえで `settings.json` の `deny` に:

```json
"Read(.env)",
"Read(./**/.env.*)",
"Read(**/*.pem)"
```

を入れて、AI が接続文字列を読めないようにしています。
読めないものは、貼り付けられません。

---

## この構成の穴

**チャット（Cowork）から MCP 経由で Supabase を叩く経路には、この歯止めが効きません。**

`guard-sql` は手元の Claude Code の `PreToolUse` フックなので、
チャット側の MCP 呼び出しは通りません。承認モードもスキップに設定しているので、
チャットからの `execute_sql` は、実質そのまま実行されます。

塞ぎ方は分かったので、別ページに分けました → **[06 チャット側の穴を塞ぐ](06-supabase-mcp.md)**

要点だけ:

- 最初に考えた「エージェント用の Postgres ロールを作って `GRANT` を落とす」は **効きません**。
  MCP は Management API 経由で開発者アカウントの権限で動くので、ロール権限の上を通ります
- 実際に効くのは接続 URL のパラメータ。`read_only=true` でサーバー側が読み取り専用ユーザーに切り替わり、
  `project_ref=<id>` で対象プロジェクトが 1 つに限定されます
- 本番プロジェクトは MCP に繋がない。Supabase 自身がそう書いています

ロール分離自体は、**接続文字列で直接 Postgres に繋ぐ経路**（ローカルの psql、
スクリプト、アプリのサービスアカウント）には効きます。
そちらのテンプレートは [kit/supabase/agent-readonly-role.sql](../kit/supabase/agent-readonly-role.sql) に置きました。
