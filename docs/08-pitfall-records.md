# 08. 落とし穴を機械可読にする

English: [08-pitfall-records.en.md](08-pitfall-records.en.md)

このリポジトリの落とし穴は、長いあいだ散文で書かれてきました。読み物としては
それでいいのですが、2 つ困ることがあります。

1. **検査ツールから参照できない。** 「`grammar === 'shell'` の分岐が消えたら
   `--sql` の後ろが再び消える」と docs に書いてあっても、それを見張るものがない
2. **確度が混ざる。** 「自分の環境で実際に測った」「他の観測から導いた」「公式
   ドキュメントにそう書いてある」「断定したが確かめていない」が、同じ地の文に並ぶ

`data/pitfalls/` は、この 2 つだけを解くための場所です。散文を置き換えるもの
ではありません。docs は引き続き経緯を書き、レコードは「何が、どの確度で、
いま塞がっているか」だけを持ちます。

---

## 置き場所

| | |
|---|---|
| `data/pitfalls/` | このリポジトリのツールと環境の落とし穴。1 穴 1 ファイル |
| `data/app-pitfalls/` | アプリ実装側の落とし穴。スキーマは共通。まだ空です |
| `data/pitfalls/_schema.json` | 定義そのもの。バリデータはこれを読んで動きます |
| `data/pitfalls/_template.json` | 1 件足すときにコピーする雛形 |
| `data/pitfalls.index.json` | 生成物。コミットします。CI が再生成して差分が出たら赤 |

`_` で始まるファイルはレコードではありません。

**1 ファイルに配列でまとめていない理由**は、[事例](case-studies/beauty-matching.md)に
書いてあります。1 枚の大きな台帳は、270KB に達した時点で書き込めなくなり、
記録されない変更が 11 本溜まりました。1 穴 1 ファイルなら、Issue から 1 件足すのは
ファイルを 1 つ置くだけで、他の PR とぶつかりません。

---

## 確度は 4 値

| 値 | 意味 |
|---|---|
| `measured` | 自分の環境で実際に測った。再現手順が `repro` にある |
| `inferred` | 引用したコードや設定から導いた。実行した記録はない |
| `documented` | 公式ドキュメントにそう書いてある。`sources` に URL がある |
| `unverified` | 断定されているが、根拠も導出も書かれていない |

**迷ったら低い方に倒します。** docs の元の文が「実測」と書いていても、どう測ったかが
書かれていなければ `unverified` です。これは書き手を疑うためではなく、**あとから
確かめ直せる場所を残す**ためです。

そして、この規約は機械で守られています。`summary` / `fix` / `why_not_closed` に
「実測」「測定した」「検証済み」「確認済み」「measured」のいずれかが出てきたら、
`confidence` が `measured` でない限りバリデータが落とします（規則 R11）。
`title` は対象外です。docs の見出しをそのまま引いた題名まで取り締まると、
使いにくいだけなので。

---

## 測定環境と `"unrecorded"`

`measured` のレコードは `environment` を持ちます。5 つのフィールドが必須です。

```json
"environment": {
  "os": "unrecorded",
  "shell": "unrecorded",
  "shell_version": "unrecorded",
  "claude_code_version": "unrecorded",
  "node_version": "20"
}
```

値が分からないときは、**推測せずに `"unrecorded"` と書きます**。省略はできません。
「書き忘れた」と「記録が無い」を区別できなくなるからです。

環境が分からないことと、測っていないことは別です。だから環境が全部 `"unrecorded"`
でも `measured` のままにします。**鮮度は別の軸**として扱います。

**`measured_on` は例外で、`"unrecorded"` を取りません。** 実日付（`YYYY-MM-DD`）が必須です。
測った日が無い記録は、古くなったかどうかを判定できません。測った対象が動いたときに
「測り直すべきもの」として拾えない記録は、鮮度の軸に載せられないからです。
日付が出てこないなら、それは測定として扱わず確度を下げます。

### `stale_risk`

`data/pitfalls.index.json` を作るときに計算する派生値で、レコードには書きません。

| 値 | いつ |
|---|---|
| `unknown_version` | `layer` が `permissions` か `hook` で、`claude_code_version` が `"unrecorded"` |
| `ok` | 環境が記録されている、またはその層が Claude Code のバージョンに依存しない |
| `not_applicable` | 測定ではないので、古くなる環境がそもそも無い |

`permissions` と `hook` を特別扱いするのは、**測っている対象が Claude Code 自身**
だからです。どのバージョンで測ったか分からない `deny` の挙動は、いまも同じとは
言えません。手で書く「最終確認日」は書いた翌日から嘘になるので、計算しています。

## 種別と対処の状態

| `kind` | 意味 | `status` |
|---|---|---|
| `trap` | 踏むと事故になるもの | **必須** |
| `limitation` | 塞ぎようがない、あるいはまだ分かっていない限界 | **必須** |
| `behaviour` | 穴ではなく、知っておくべき挙動 | **書いてはいけない** |

`status` は `closed`（塞いだ）/ `open_recorded`（塞がずに穴として記録）/
`untouched`（未対応）の 3 値です。`closed` なら `fix`、`open_recorded` なら
`why_not_closed` が要ります。**塞がずに残すなら、残す理由を書かせる**ということです。

`behaviour` に `status` を持たせないのは、「deny は allow に勝つ」のような記録を
「未対応の穴」として数えたくないからです。

---

## `severity` は測定値ではない

`severity`（`high` / `medium` / `low`）は、**書き手がその穴をどれくらい重く見たか**です。
測ったものでも、どこかに書いてあったものでもありません。`confidence` とは完全に独立した軸で、
`unverified` の穴に `high` が付くこともあれば（危なそうだがまだ確かめていない）、
`measured` の挙動に `low` が付くこともあります。確度が高いことと、重いことは関係ありません。

したがって `severity` にはクレームゲート（R11）がかかりません。かける意味がないからです。
数える側も、`severity` の分布を「このリポジトリがどれくらい危ないか」の指標として
読まないでください。読むなら `status` と `stale_risk` の方です。

**`severity` は全部 Claude が付けたものです。** レコードを書いた時点で人間が確認して
いません。見直して付け替えて構いませんし、そのための軸です。

## `origin` — どこに書いてあるか

```
"origin": "docs/02-guardrails.md#3-つ目は賢くしたせいで空きました"
```

ファイルパスと見出しアンカーです。バリデータは、そのファイルが実在すること、
アンカーがそのファイルの見出しに一致すること、そして**行番号の形が来ていないこと**を
見ます。行番号は 1 行足しただけで黙ってずれます。見出しが変われば CI が赤くなります。

### 散文がまだ無いとき

「散文が先」を規則にすると、**3 行の見出しスタブを置けば通ります。** スタブと本物の
散文は機械から区別できません。つまりこの規則は静かに形式に落ちて、しかも docs が
スタブで太る方向に落ちます。だから逃げ道を隠さずに用意してあります。

| `origin` | いつ使うか |
|---|---|
| `docs/02-guardrails.md#見出し` | 散文がある。ファイルとアンカーの両方を検査します |
| `issue:42` | 報告が出所。このリポジトリの Issue 番号です |
| `record` | このレコードが初出。まだどこにも書いていません |

後ろの 2 つは無料ではありません。インデックスが `has_prose: false` を派生させて
`counts.without_prose` に数えます。**データにだけ在って docs に無い穴が何件あるか**が
毎回出ます。これが増え続けたら、docs がデータに追いつくのをやめたということです。

順序に 1 つ罠があります。`issue:42` はコロンのあとが数字で終わるので、**行番号の検査に
先に食われます**（`:[0-9]+$`）。形の判定を先に置いて、行番号の検査は散文の形にだけ
当てています。`issue:0` や `issue:abc` のような惜しい間違いは「行番号だ」ではなく
「issue の形になっていない」と言います。読む人を違う場所に探しに行かせないためです。

## `detection` — 検査ツールが読む場所

```json
"detection": {
  "checkable": true,
  "kind": "file-content",
  "target": "kit/claude/hooks/guard-sql.mjs",
  "pattern": "grammar === 'shell'",
  "expect": "present",
  "message": "シェル文法の分岐が消えると、--sql の後ろが再びコメント扱いで消える。"
}
```

`expect` が肝で、`present`（無ければ赤）と `absent`（有れば赤）を区別します。
これが無いとパターンだけでは向きが分からず、データとして使えません。

`checkable: false` のものは、なぜ機械で見られないかを `note` に書きます。
`permissions` 層はほぼ全部これです。判定しているのは Claude Code 本体で、
こちらのコードではないからです（[02](02-guardrails.md)）。

`checkable: true` のものは、インデックスの `checks` 配列に平らに並びます。
外部のツールはそこだけ読めば済みます。

`node kit/scripts/lint-pitfalls.mjs` で、`checkable: true` のレコードが持つ検査を
まとめて実行できます。合格・違反・判定不能を分け、自動検査できないレコードの件数も
表示します（件数はレコードが増えれば増えるので、ここには書きません）。
検査の範囲と終了コードは [11. 落とし穴の静的検査](11-pitfall-linter.md) を参照してください。

## 1 件足す

1. `data/pitfalls/_template.json` を `data/pitfalls/<id>.json` にコピーする
2. 埋める。使わないキーは**消す**。余っているキーはエラーになります
3. 検査して、インデックスを作り直す

docs にまだ書いていない観測なら、`origin` は `record`（初出）か `issue:<番号>`
（報告が出所）です。**先に docs を書く必要はありません。** 散文はあとから足せます。

```bash
node kit/scripts/validate-pitfalls.mjs
node kit/scripts/test-validate-pitfalls.mjs
node kit/scripts/build-pitfall-index.mjs
```

CI（`pitfalls` ジョブ）が同じことをして、インデックスに差分が出たら赤くします。
レコードだけ足してインデックスを作り直し忘れると、検査ツールは昨日のデータを
読み続けるので、そこは機械で止めます。

Issue から報告するだけでも構いません。レコードにするのはこちらでやります
→ [落とし穴の報告テンプレート](https://github.com/ponponpon888/ai-workforce/issues/new?template=pitfall.yml)

## 検査の一覧

`_schema.json` の `rules` がそのまま出典です。

| | |
|---|---|
| R01 | ファイル名が `<id>.json` と一致する |
| R02 | 必須フィールドが揃っていて、知らないフィールドが無い |
| R03 | 型と enum の値が正しい |
| R04 | `id` が `^[a-z][a-z0-9]*-[0-9]{3}$` |
| R05 | `measured` ⟺ `measured_on` / `environment` / `repro` が揃う |
| R06 | `environment` はちょうど 5 フィールド。値か `"unrecorded"` |
| R07 | `documented` は `sources` が 1 件以上 |
| R08 | `inferred` は `inferred_from` が 1 件以上 |
| R09 | `behaviour` は `status` 禁止、`trap` / `limitation` は必須 |
| R10 | `closed` は `fix` 必須、`open_recorded` は `why_not_closed` 必須 |
| R11 | 実測を名乗れるのは `measured` のレコードだけ |
| R12 | `related` の参照先が実在する |
| R13 | `origin` が既知の形。散文の形ならファイルが実在し、行番号形式でない |
| R14 | `origin` のアンカーが、そのファイルの見出しに一致する（散文の形のみ） |
| R15 | `checkable` なら `target` / `pattern` / `expect` が要る |
| R16 | `measured_on` は実日付（`YYYY-MM-DD`）。`"unrecorded"` は通らない |
| R17 | ファイルが JSON として読め、オブジェクトである |
| R18 | `id` が全レコードで一意 |

反例は 1 ルールにつき 1 つ以上あり、**ルール名まで照合しています**。
全部を「何かがおかしい」で落とすバリデータなら、そのテストは通ってしまうので。

## 正直に書いておくこと

- **docs がデータに追いついていません。** `origin` が `record`（初出）のレコード、つまり
  散文がまだ無いものが常に何件かあります。件数は `data/pitfalls.index.json` の
  `counts.without_prose` に出ます。これが増え続けたら、docs がデータに追いつくのを
  やめたということです。
- **`environment` が全フィールド `"unrecorded"` のレコードがあります。** 古いものは、
  測定日こそ測った本人から聞き出して docs に書き足しましたが、OS もシェルも
  `claude_code_version` も、どこにも記録がありませんでした。埋まっているのは、
  測りながら書いたものだけです。`claude_code_version` はほとんどのレコードで
  `"unrecorded"` なので、`permissions` と `hook` のレコードは大半が
  `stale_risk: unknown_version` から始まります。
- **正例のテストは、先に赤くできませんでした。** 反例は、ルールが 1 つも無い
  バリデータに対して全部落ちることを先に確かめてあります。正例は「何もしない
  バリデータが正しいレコードを受け入れる」ので、原理的に先に赤くできません。
  [02](02-guardrails.md) に書いた「塞ぐ側のテストしか先に落とせない」が、
  ここにもそのまま出ています。

### 件数をここに書かない理由

以前このページは「いま 12 件しか入っていません」「候補は 140 件」のように件数を
本文に書いていました。レコードが増えるたびに嘘になり、実際に嘘になっていました。

件数は `data/pitfalls.index.json` が持っています。生成物なので、レコードを足して
インデックスを作り直せば必ず合います。CI は作り直して差分が出たら赤くします。

```bash
node -e "const j=require('./data/pitfalls.index.json'); console.log(j.counts)"
```

散文に書いた数字は、書いた翌日から嘘になり得ます。`measured_on` を手書きの
「最終確認日」にしなかったのと同じ理由です。

**ただし、日付と対象コミットを明記した測定の記録は別です。**
[17. 修正の統合状況](17-integration-status.md) は「このコミットを、この日に、この環境で
測ったらこうだった」という記録なので、いまの件数と違っていても嘘ではありません。
書き換えたら、むしろ記録を壊します。

区別は「いま何件あるか」を言っているか、「いつ測ったら何件だったか」を言っているかです。
前者は生成物に任せ、後者は日付と対象を添えて凍結します。
