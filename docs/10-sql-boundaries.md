# SQLガードの境界と承認

SQLガードのNode版とPowerShell版を同じ方針で修正しました。対象は事故防止用の入力検査です。SQL全体の構文解析器や、DB側の権限制御ではありません。

## WHEREの所属を確認する

更新・削除の各キーワードについて、同じ括弧の深さにWHEREがあるかを確認します。サブクエリやCTE内のWHEREを、外側の全件更新の条件として数えません。条件付きの通常の更新・削除は引き続き通ります。

## 未対応として停止する経路

- DOブロック。引用された本文が実行されるため、通常の文字列として無視できません。
- SQLファイル内の行頭の `\i` / `\ir`。参照先の再帰検査は未実装です。
- 検出したファイルのどれかが読めない場合。1件読めただけでは通しません。
- ファイル経由のDDL。コマンドだけの承認ではファイル内容を固定できないため、承認トークンがあっても停止します。
- SQLガード内部の検査エラー。不正JSONなどを成功として扱わず、exit 2で停止します。

ファイル経由DDLを扱うには、レビュー済みのSQL本文そのものを承認し、その本文を直接受け取る実行経路へ渡してください。承認ツールの `--file` / `-Path` はSQL本文を読み込むためのオプションであり、`psql -f ...` の実行コマンドを承認する機能ではありません。未対応経路を別の書き方で通すことは、このガードの検証範囲を外れます。

DOの扱いの根拠: [PostgreSQL公式 DO](https://www.postgresql.org/docs/current/sql-do.html)。DOは匿名の処理ブロックを実行します。

## 承認の変更

承認ハッシュは `aiwf-exact-v2` とNULによる識別子を付けた、入力文字列のUTF-8表現から生成します。連続空白・改行・文字列内部の空白を正規化しません。承認ファイルの本文も、実行入力と一致する必要があります。

トークンは一意な消費済み名へ原子的に移動してから検査します。同時に呼び出されても取得できるのは1つだけです。期限切れ、未来の時刻、本文不一致、取得失敗は拒否します。取得したトークンは戻しません。消費済みファイルの削除に失敗しても、元の承認名には残りません。

**旧形式の承認は無効です。** フックと承認ツールを両方更新し、SQLを再確認して承認し直してください。期限は引き続き15分です。トークンは接続先のDBやプロジェクトにはまだ結び付いていません。また、ローカルファイルを自由に変更できる主体に対する権限の境界ではありません。

## 検証と残る制限

```powershell
node kit/scripts/test-guard-sql.mjs
node kit/scripts/test-sql-boundaries.mjs
node kit/scripts/test-sql-boundaries.mjs --target ps
node kit/scripts/test-sql-boundaries.mjs --target ps --pwsh powershell.exe
```

追加スイートは18ケースで、同じ入力を両実装へ送れます。SQLや入力されたシェルコマンドを実行せず、一時ファイルとガードの終了コードを検査します。同時呼び出し6件のうち1件だけが承認を取得するケースも含みます。

今回のLinux / Node v24.19.0では、追加18件と既存44件が成功しました。PowerShell実行はこの環境では未確認で、既存CIのPowerShell 7・Windows PowerShell 5.1ジョブに同じ追加スイートを組み込んでいます。ローカル成功はホスト全体での動作確認を意味しません。

正規表現と括弧の深さによる検査なので、全SQL方言、動的SQL、特殊な引用、全クライアント、任意のMCP名、実行時のファイル差し替えを保証しません。WHEREの存在は、対象件数が少ないことや会社境界が正しいことも保証しません。SQLファイル内の全クライアント命令に対応したわけではありません。

外部のホストがフックを起動しなかった場合や、フックの起動失敗・タイムアウトは、スクリプト内部のexit 2では制御できません。導入状態の確認と接続先の権限制御は別に必要です。
