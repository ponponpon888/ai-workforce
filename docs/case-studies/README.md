# 事例

このディレクトリのドキュメントには、実際に稼働しているサービスから
**動いているコードの断片**と、**そこで何が起きたか**を載せます。

書き方のルール:

1. **抽象論を書かない。** 「設計が大事」ではなく、そのプロジェクトで実際に書いた行を貼る
2. **失敗を先に書く。** うまくいった話より、踏んだ穴の方が読む価値がある
3. **秘密を貼らない。** 接続文字列、キー、顧客データ、テーブルの実データは載せない
4. **匿名の案件は、匿名のまま具体的に書く。** 名前を伏せることと、中身を薄くすることは別

| 事例 | 中身 |
|---|---|
| [Hanami Nail](hanami-nail.md) | RLS は行を守るが列を守らない／冪等性 4 通り／機能追加が既存の検証を脆弱性に変えた |
| [美容領域のマッチングプラットフォーム](beauty-matching.md) | マッチングを意図的に捨てた／遷移表のない状態機械／Markdown 台帳が 2 回壊れた |
| [MUSUBU](musubu.md) | 署名検証／**片方だけ冪等な webhook**／LLM に嘘をつかせない戦い／文字化け地獄 |

## 秘匿方針

- Hanami Nail は実名。管理者の個人メール、Supabase のプロジェクト ref、
  未公開サロンの実名、提携サロンの料金は伏せています
- 美容領域のマッチングプラットフォームは匿名。加えて、業種が特定できる列名を
  `practitioner_*` に置換しています（**構造は変えていません**）
- MUSUBU は実名。テナントの認証情報はもともとコードに存在しません（DB 保管）
